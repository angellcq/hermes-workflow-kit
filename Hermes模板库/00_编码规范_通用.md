# 通用编码规范（跨语言 · Hermes 默认约束）

> **模板编号**: 00 ｜ **环节**: 全生命周期 ｜ **填写人**: Hermes
> **用法**: 项目根 `AGENTS.md`/`.hermes.md` 未声明语言规范时，使用本文档作为默认约束；具体语言细节见模板 11
> **硬规则**: 项目级规范优先级高于本规范；本规范仅作为"缺失时的兜底"
> **跨语言适用**: 适用于任何语言/任何规模的项目，作为最低门槛的工程纪律

## 一、核心原则：不可变性

**始终创建新对象，绝不修改现有对象。**

```
// ❌ 错误：原处修改
modify(original, field, value) → 改变了 original

// ✅ 正确：返回新副本
update(original, field, value) → 返回新对象，original 不变
```

**理由**：
- 不可变数据防止隐藏副作用，简化调试
- 支持安全并发（无需锁）
- 便于回滚与版本控制
- 测试更容易（输入输出一一对应）

**语言特例**：
- 强类型编译型语言：默认不可变（Go: 值类型/Rust: 所有权）
- 动态语言：用 dataclass/Pydantic/record + `frozen=True`/`@dataclass(frozen=True)` 实现
- 函数式语言：天然支持

## 二、文件组织

| 原则 | 说明 |
|------|------|
| **多小文件 > 少大文件** | 高内聚、低耦合 |
| **典型大小** | 200-400 行 |
| **上限** | 800 行（单文件最大行数） |
| **组织方式** | 按功能/领域组织（不是按类型：controller/service/dao/） |
| **提取工具类** | 重复代码超过 3 次必须提取 |

**按领域组织 vs 按类型组织的对比**：

```
❌ 按类型组织（传统 Java 风格）：
src/
├── controller/      # 所有 controller
├── service/         # 所有 service
├── dao/             # 所有 dao
└── model/           # 所有 model
# 问题：改一个功能要跨多个目录

✅ 按领域组织（DDD 风格）：
src/
├── user/
│   ├── controller.ts
│   ├── service.ts
│   ├── repository.ts
│   └── model.ts
├── order/
│   ├── controller.ts
│   ├── service.ts
│   ├── repository.ts
│   └── model.ts
# 优点：改一个功能集中在一个目录
```

## 三、命名规范（通用）

| 元素 | 强类型编译型 | 动态/解释型 | 前端 | 数据库 |
|------|------------|------------|------|--------|
| **类/类型** | PascalCase | PascalCase | PascalCase | - |
| **函数/方法** | camelCase | snake_case (Python) / camelCase (JS) | camelCase | - |
| **变量** | camelCase | snake_case (Python) / camelCase (JS) | camelCase | - |
| **常量** | UPPER_SNAKE | UPPER_SNAKE | UPPER_SNAKE | - |
| **包/命名空间** | lowercase | lowercase | kebab-case | - |
| **文件名** | 与类同名 | snake_case | PascalCase (组件) / kebab-case | snake_case |
| **表名** | - | - | - | 复数 snake_case |
| **字段名** | - | - | - | snake_case |

**通用禁词**：
- ❌ 缩写晦涩：`mgr` `util` `handler`（除非项目约定）
- ❌ 单字母变量：`a` `b` `x`（循环索引除外）
- ❌ 类型前缀：`strName` `iCount`（现代语言不需要）
- ✅ 业务语义：`customerName` `activeOrderCount`

## 四、错误处理（通用）

### 4.1 通用原则

| 层 | 错误处理方式 |
|----|------------|
| **用户界面** | 友好错误提示（不暴露内部细节） |
| **API 层** | 标准化错误响应（HTTP code + message + trace_id） |
| **业务逻辑** | 抛自定义异常 / Result<T, E>；附上下文 |
| **数据访问** | 详细日志 + 重试 + 上抛 |
| **基础设施** | 监控告警 + 自动恢复 |

### 4.2 禁止事项

- ❌ 静默吞掉错误（`catch {}` / `except: pass`）
- ❌ 用 `null`/`None` 代替错误信号
- ❌ 把异常字符串硬编码到 UI
- ❌ 在循环中重复抛同一个异常（应收集后聚合抛）

### 4.3 推荐做法

- 自定义异常类层级（领域异常 vs 系统异常）
- 错误日志带 trace_id；不打印敏感信息
- 关键错误上报监控系统（Sentry / 阿里云 SLS / Prometheus）

## 五、输入验证（通用）

| 原则 | 说明 |
|------|------|
| **系统边界必验证** | API 入口 / CLI 参数 / 文件读取 / 第三方响应 |
| **基于 schema 验证** | JSON Schema / TypeScript 类型 / Pydantic / Bean Validation |
| **快速失败** | 错误立即抛出，不带病运行 |
| **清晰错误消息** | 指明哪个字段、什么值、为什么错 |
| **不信任外部数据** | API 响应、用户输入、文件内容一律验证 |

**示例**：

```python
# Python + Pydantic
class CreateUserRequest(BaseModel):
    name: str = Field(..., min_length=1, max_length=50)
    age: int = Field(..., ge=0, le=150)
    email: str = Field(..., regex=r"^[\w.+-]+@[\w-]+\.[\w.-]+$")
```

```typescript
// TypeScript + Zod
const CreateUserRequest = z.object({
  name: z.string().min(1).max(50),
  age: z.number().int().min(0).max(150),
  email: z.string().email(),
});
```

```java
// Java + Bean Validation
public class CreateUserRequest {
    @NotBlank @Size(min=1, max=50)
    private String name;
    @Min(0) @Max(150)
    private Integer age;
    @Email
    private String email;
}
```

## 六、测试规范（通用）

### 6.1 测试金字塔

```
       /\
      /  \      E2E（少量，关键路径）
     /----\
    /      \    集成测试（中等，跨模块）
   /--------\
  /          \  单元测试（大量，单函数/方法）
 /------------\
```

### 6.2 覆盖率门槛（按语言类型）

| 语言类型 | 单元覆盖率 | 集成 | E2E |
|---------|----------|------|-----|
| 强类型编译型 | ≥80% | ≥60% | 关键路径 100% |
| 动态解释型 | ≥80% | ≥60% | 关键路径 100% |
| 脚本型 | ≥60% | ≥80%（部署/迁移脚本必测） | - |
| 前端 | ≥70% | ≥50% | 关键路径 100% |
| 移动端 | ≥70% | ≥50% | 关键路径 100% |

### 6.3 测试编写纪律

- **FIRST 原则**：Fast（快）/ Independent（独立）/ Repeatable（可重复）/ Self-validating（自验证）/ Timely（及时）
- **AAA 模式**：Arrange（准备）/ Act（执行）/ Assert（断言）
- **测试名描述行为**：不要 `test1` `testMethod`，要 `should_return_error_when_user_not_found`
- **每个测试只测一件事**：多断言拆多个测试

### 6.4 测试数据

- 工厂模式生成测试数据（factory_boy / test-data-bot）
- 数据库测试用事务回滚，不污染真实数据
- 敏感数据脱敏或用 fake 数据

## 七、版本控制规范（Git）

### 7.1 提交消息格式（Conventional Commits）

```
<类型>(<范围>): <描述>

<可选正文>

<可选页脚>
```

| 类型 | 用途 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `refactor` | 重构（既不修复 bug 也不添加功能） |
| `docs` | 文档变更 |
| `test` | 添加/修改测试 |
| `chore` | 杂项（构建/工具/依赖） |
| `perf` | 性能优化 |
| `ci` | CI/CD 变更 |
| `style` | 代码格式（不影响逻辑） |

**示例**：

```
feat(auth): add JWT refresh token rotation

- Add refresh token endpoint
- Implement rotation strategy
- Update auth middleware

Closes #123
```

### 7.2 分支策略（推荐 Git Flow 简化版）

```
main (生产)
  ↑
release/* (预发布)
  ↑
develop (开发集成)
  ↑ ↑ ↑
feature/*  feature/*  feature/*
```

或 **GitHub Flow**（适合持续部署）：

```
main
  ↑
feature/* (直接合并到 main)
```

### 7.3 拉取请求（PR）规范

1. **标题**：与提交消息一致（feat: xxx）
2. **描述模板**：
   - 改了什么（一句话）
   - 为什么改（背景）
   - 怎么测（测试计划）
   - 影响范围（哪些模块/服务）
   - 截图（UI 改动）
3. **审查清单**：
   - [ ] CI 通过
   - [ ] 覆盖率达标
   - [ ] 文档已更新
   - [ ] 至少 1 名审查者通过

## 八、安全规范（通用底线）

| 类别 | 规范 |
|------|------|
| **敏感信息** | 不入库；用环境变量/密钥管理（Vault/AWS Secrets Manager） |
| **SQL 注入** | 参数化查询；ORM；禁止字符串拼接 |
| **XSS** | 输出转义；CSP 头；不信任用户 HTML |
| **CSRF** | Token 验证；SameSite cookie |
| **认证** | 不自己实现；用成熟库（JWT/OAuth2/SAML） |
| **密码** | bcrypt/argon2；不存明文；最小长度 + 复杂度 |
| **日志** | 不打印密码/token/PII；日志收集后审计 |
| **依赖** | 定期更新；漏洞扫描（npm audit/safety/trivy） |
| **HTTPS** | 全站 HTTPS；HSTS 头 |
| **权限** | 最小权限原则；RBAC；越权检查 |

## 九、性能规范（默认底线）

| 类别 | 规范 |
|------|------|
| **数据库** | 索引覆盖查询；避免 N+1；分页 |
| **缓存** | 读多写少用缓存；TTL 设置；失效策略 |
| **API** | 响应 < 500ms；分页；字段过滤 |
| **前端** | 首屏 < 3s；包大小监控（bundle analyzer） |
| **异步** | IO 密集型异步；CPU 密集型多进程 |
| **资源** | 连接池；线程池；对象池 |
