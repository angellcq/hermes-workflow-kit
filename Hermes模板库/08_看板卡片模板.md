# 看板卡片模板（合并版）
> **模板编号**: 08 ｜ **环节**: 看板同步（S7，贯穿全程） ｜ **维护人**: Hermes
> **事实源声明**: 任务状态一律以框架内置 `hermes kanban` 为事实源；本模板的 JSON 结构仅作卡片设计参考与离线记录格式，不另建平行看板。聊天中的口头进度仅为输入信号，须核实后落板
> **schema 口径**: 看板真实字段以 `PRAGMA table_info(tasks)` 为准（39 列，无 `depends_on`/`updated_at` 列；依赖在 `task_links` 表）。落库状态为 9 态真名：`triage/todo/scheduled/ready/running/blocked/review/done/archived`；本模板正文使用的 in_progress/in_review 为文档口径词，对照：in_progress→`running`、in_review→`review`、todo(待办)→`ready`（等父卡时为 `todo`）。机制细节与操作规程见 `skills/kanban-executor/references/kanban机制说明书.md` 与 `skills/kanban-executor/SKILL.md`
> **assignee 语义**: 路由键而非负责人备注——**`cc-<角色>`**（如 `cc-backend-developer`）= 派给对应 Claude Code 子 agent；**`hm-<用途>`**（如 `hm-analysis`）= Hermes 主会话自己做。**禁止填真实 Hermes profile 名（`default` 等）**，否则网关 dispatcher 会抢单自跑。真实 profile 名单见 `hermes kanban assignees`
> **负责人派生（v5.0）**: 卡面「负责人」不手填，由 assignee 前缀派生——`cc-*` → Claude Code（括号内角色），`hm-*` → Hermes。一个字段一个事实源，避免"assignee 派给 A、负责人写 B"打架
> **规则**: 状态变更立即同步｜卡片必须带完整上下文链接（任务卡/PRD/HLD/DD）｜每日收工生成看板摘要｜所有 kanban 命令显式带 `--board <板>`

## 二、状态口径

### 2.1 卡面三态 ↔ 板 9 态映射（v5.0 唯一口径）

| 卡面三态（人看） | 板真态（机器） | 出现条件 |
|---|---|---|
| **待执行** | `todo` | 已建卡、父卡未完成（依赖等待专用态） |
| **待执行** | `ready` | 父卡全 done，可被派发器认领 |
| **待执行**（异常子态） | `blocked` | 派发失败达上限 / 缺输入待人工 |
| **待执行**（异常子态） | `scheduled` | 等时间窗口（不是等人） |
| **待执行**（异常子态） | `triage` | 需求过粗待分诊（也是同因循环 ≥2 次的兜底态） |
| **正在运行** | `running` | 派发器 `claim` 成功（写 claim_lock + claim_expires） |
| **正在运行**（复核子态） | `review` | 开发交付、等验收人接单（**不是阻塞**） |
| **已完成** | `done` | 验收通过 + `complete --summary`（必须有证据） |
| **已完成**（终态） | `archived` | 收尾卡 `archive`，板面归零 |

> 卡面只写三态；`blocked/scheduled/triage/review` 一律归入「待执行」并在备注栏标注原因。**不改板 schema、不改 9 态真名。**
> 旧文档词对照：`in_progress` → `running`；`in_review` → `review`；`todo(待办)` → `ready`（等父卡时为 `todo`）。

### 2.2 流转规则（谁触发 + 前置条件）

| # | 从 | 到 | 触发者 | 前置条件 | 命令 |
|---|---|---|---|---|---|
| 1 | — | `todo` | Hermes 建卡 | 上游 DD 完成；卡字段齐（阶段/assignee/依赖/files_scope/DoD 非空） | `create --assignee <cc-x\|hm-x>` + `link` |
| 2 | `todo` | `ready` | 板（自动） | 全部父卡 `done` | 板自动 `recompute_ready`；卡死时人工 `promote` |
| 3 | `ready` | `running` | **派发器** | ①父卡全 done ②assignee 前缀合法 ③无同卡存活进程 ④并发额度未满 ⑤执行端探活通过 | `claim <id> --ttl 3600` → 起 lane → 每 10min `heartbeat` |
| 4 | `running` | `running` | 派发器 | 每 <15min 心跳（否则 TTL 回收） | `heartbeat <id> --note ...` |
| 5 | `running` | `review` | 派发器代写 | lane 退出码 0 且 `git diff` 非空 | `request-review <id>` |
| 6 | `review` | `running` | 验收人（Hermes） | 验收开始 | `claim <id>` |
| 7 | `review` | `ready` | 验收人 | 验收不通过（附证据） | `request-changes <id>` / `reopen-review <id>` |
| 8 | `running` | `done` | 验收人 | DoD 逐条通过 + 独立构建/测试证据 | `complete <id> --summary "<证据>"` |
| 9 | `running` | `blocked` | 派发器 | 派发失败 ≥3 或崩溃 ×2 或前置缺失 | `block <id> "<原因>"` |
| 10 | `blocked` | `ready` | Hermes（人工） | 阻塞原因解除 | `unblock <id>` |
| 11 | `done` | `archived` | Hermes（收尾卡） | 交付报告归档 + 追踪矩阵闭环 | `archive <id> --summary "<结论>"` |

> **禁止流转**：`ready → done`（跳级）、`todo → running`（未满足依赖）、`running → ready`（除 TTL 回收并记 comment）。
> **两条硬提醒（实测）**：① `--initial-status running` **不能**替代 `claim`——无 `claim_lock/claim_expires` 的 running 卡会被 `reconcile_orphaned_running` 在下一 tick（约 60 秒）打回 `ready`；② `unlink` 的瞬间子卡即满足依赖→立刻变 `ready`，若此时有派发器在跑会被立即派出去（双派经典路径），`unlink` 前必须确认父卡产出已落盘。
