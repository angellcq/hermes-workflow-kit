# 管理后台结构重构 / 功能合并的核查表

适用：服务端渲染或轻量前端的管理后台里，菜单改名/分层/移动、两个页面合并为一个、权限点随之下线。目标是在 PRD 最前面就能给出“有没有数据迁移、波及哪些面、哪一步最可能翻车”。

## 1 先判菜单来源（决定改动面）

- 静态布局页（Razor / JSP / Blade 里手写 `<li>`）→ 改一个文件即可，无需后端。
- 接口下发或菜单表 → 菜单实体、缓存、前端渲染三处都要改，还要考虑存量菜单记录的迁移。
- 证伪：在布局/菜单组件里找硬编码的导航项，并确认库里有没有菜单表；两者都没有才是真静态。

## 2 关联面清单（逐项给结论，没有的也要写“没有”+ 证伪命令）

路由跳转｜面包屑｜页签缓存｜菜单高亮｜快捷搜索/命令面板｜权限码｜i18n 文案｜页面 `<title>` 与页头标题｜导出文件名与 sheet 名｜对外硬链（书签、IM 快捷入口、其它系统的链接）。

- 高亮与父级展开是**两处逻辑**：父级是否渲染（任一子项有权限）与父级是否展开/高亮（当前路径前缀匹配）常写在不同变量里；改层级时两处都要改，否则出现“看得见但不展开”。
- 父级容器通常不绑权限码。引入父级码会让权限行总数与全部存量角色配置一起变；除非需求明确要求能单独授权“空分组”，不要主动加。

## 3 合并前先核对数据源

- 列出两侧的读表与写表。**同一张主表 + 同一主键** ⇒ 合并只是把两个页面放到一起：零数据迁移、零字段冲突、可逆（回滚代码即恢复两页）。这个结论要写在 PRD 最前面，因为它决定后面整章的写法。
- 不同表 ⇒ 才需要字段映射表、迁移脚本、回滚方案，并明确回答“是否可逆”。
- 字段映射表只做三件事：同名列保留；单侧字段不并入主列表；**同名但语义不同的字段禁止合并**（典型：列表里的税率值是 `13`，同步结果里的销项税 ID 是 `3`，看起来都叫“销项税”）。

## 4 1:N 明细不要摊进主列表

主表 : 明细表 = 1:N（如商品 : 组织税率）。主列表一行 = 一个主实体；把明细 JOIN 进来会让“共 N 条”与行数脱节，并破坏“按主键整体删除”的语义。明细留在详情区或同步结果区展示。

## 5 分页口径自查（合并后列表成为唯一入口时必查）

- 数据查询带 JOIN 派生列时，COUNT 必须与数据查询同口径：`COUNT(DISTINCT 主键)`，或把数据查询改造成一行一实体。
- 症状：关键字查询 total 小于当页实际行数、末页空白、翻页跳条。
- 修法会改变用户已熟悉的“总条数”口径，属业务语义 → 进决策队列，给“只改 COUNT / 不动 / 改数据查询”三选项与各自代价。

## 6 权限码退场或换名（最易翻车的一步）

- 权限过滤器特性通常只接受一个码（`AllowMultiple = false` 之类），所以**代码层无法同时兼容新旧码**；而权限码又存在登录态里（Cookie claim），改完必须重新登录。
- 两阶段脚本，做到零中断：
  1. 备份权限关联表。
  2. 发版前：给持旧码的角色 INSERT 新码（`NOT EXISTS` 幂等）。旧代码不认新码 ⇒ 零副作用。
  3. 发版并验证后：DELETE 旧码。角色保存接口通常会校验“码必须存在”，旧码留库会让下次保存静默丢权限。
  4. 通知重新登录；重跑种子命令把新码补进超管。
- 反例（必然中断）：先删旧码再发版 ⇒ 旧页立刻 403；先发版再插新码 ⇒ 窗口期内旧角色 403。
- 映射表要覆盖每个旧码 → 新码，并注明“原本就持新码的角色零升级”，这是脚本存在的理由。

## 7 前端未转义缺口会在合并时升级为风险面

原本是边缘页的 `innerHTML` 未转义（服务端返回的 message / 名称 / 错误信息），合并后变成主入口，必须同批补齐每页各带一份的转义函数。检查点：`innerHTML` 拼接里的每个 `${}` 都要包转义。

## 8 范围声明要可验

PRD 里显式写“不改表结构 / 不改接口契约 / 不改业务逻辑 / 不引依赖”，并给一条能自动核对的约束（如 `git diff --stat` 只含清单内文件、`grep` 文案字面值零命中）。否则合并类需求极易顺手改到共用表或共用接口。
